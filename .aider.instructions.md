# Lab Infrastructure Instructions

## 0. System Prerequisites & Installation
If you are starting on a fresh server, run these commands to install the environment:

1. **Install uv (Python package manager):**
   `curl -LsSf https://astral.sh/uv/install.sh | sh`
   *(Restart your terminal or source your shell configuration after this)*

2. **Create Aider Environment:**
   `uv venv --python 3.12`
   `source .venv/bin/activate`

3. **Install Aider:**
   `uv pip install aider-chat`

4. **Verify Installation:**
   `aider --version`

## 1. Operational Rules (Non-Negotiable)
- **NO RESOURCE LIMITS:** Never add `deploy: resources: limits` (CPU/Memory) to any service. My infrastructure has ample resources; prioritize performance over restriction.
- **HARDWARE PASS-THROUGH:** Always preserve `gpus: all` or existing `devices` blocks. These are required for media transcoding and AI acceleration.
- **VARIABLE USAGE:** Use environment variables from the .env file. Do not hardcode ports, paths, or API keys.
- **USER PERMISSIONS:** Only add `user: ${PUID}:${PGID}` if specifically requested for a container.

## 2. Server Context & Architecture
- **Inclusion Pattern:** Most services are defined in individual files (`compose/serverX/<servicename>.yaml`) and are referenced/included in the main `docker-compose-serverX.yaml`. Do not redefine global networks or volumes in individual service files if they are managed by the parent YAML.
- **Networking:** Most services share the `mediaserver` network. When adding a service, ensure it is attached to the appropriate network bridge as defined in the parent `docker-compose-serverX.yaml`.
- **Modular Design:** If auditing a file in `compose/serverX/`, always cross-reference the parent `docker-compose-serverX.yaml` to verify network/volume mappings.
- **Standardized Paths:** 
  - Docker Data: `${DOCKERDIR}`
  - Secrets: `${SECRETSDIR}`
  - Media: `${MEDIASHARE}`
  - Downloads: `${USERDOWNLOAD}`

## 3. How to Configure This Workspace (Setup)
If you are setting up this Aider environment for the first time:
1. Ensure your `.env` file is in the root directory.
2. The system relies on the `DOCKERDIR` variable to locate configurations. 
3. When auditing or updating, always load the service YAML AND the parent `docker-compose-serverX.yaml` to maintain network/volume consistency.

## 4. New Service Protocol
- **Template First:** When creating a new service, first check the `templates/` directory (or equivalent standard) for an existing pattern.
- **Copy & Customize:** If a template exists, use it as the base. If not, create a standard configuration that mimics the existing style of `compose/serverX/` files.
- **Environment Parity:** New services must utilize variables for all ports, paths, and secrets.
- **Standardization:** Add the new service to the relevant `docker-compose-serverX.yaml` file to ensure it is included in the server's boot sequence.

## 5. Troubleshooting
- If a service fails to initialize after an edit, check if a GPU device or volume mount was accidentally removed.
- Always check the `logs` for the specific container if an edit causes a restart loop.

## 6. LLM Connectivity (Ollama)
- **Local Ollama:** Aider is configured to use the local Ollama instance running on the host. 
- **Configuration:** Ensure the `OLLAMA_API_BASE` environment variable is set to your Server instance (e.g., `http://<SERVER_IP>:11434`).
- **Model Usage:** Always use the `ollama_chat/` prefix (e.g., `aider --model ollama_chat/qwen2.5-coder`).

## 7. Interaction Protocol (CRITICAL)
- **READ-ONLY AUDITOR MODE:** When I ask you to "check", "audit", or "review" files, you are in READ-ONLY mode. You MUST report findings to me first and wait for my explicit command "Fix [file path]" before applying any changes.
- **NO AUTO-EDITING:** Never attempt to "fix" configuration files without explicit confirmation from the user. If you find a violation, list it, explain it, and WAIT for instructions.
- **STRICT GPU PRESERVATION:** Never delete, modify, or rename `deploy.resources.reservations` or `devices` blocks. These are strictly protected. Only `deploy.resources.limits` (CPU/Memory) are candidates for removal.
- **SURGICAL DELETION (STRICT):** If I command a fix for a violation within a nested YAML block (like `deploy:`), do NOT delete the entire parent block. You MUST preserve the `reservations` and `devices` keys. Delete ONLY the specific key that violates the rule (e.g., `limits:`).
- **FRAGILE CONFIGS:** Respect all comments in YAML files regarding network/volume locks (e.g., Nextcloud-AIO, specific hardcoded bridge names). Do not modify these unless explicitly instructed.
- **ASK FIRST:** If you are unsure if a change will break a specific service, ask the user before generating the edit.
- **PATH ACCURACY:** When reporting a violation found in an include: file, clearly specify the child file path (e.g., compose/server2/ollama.yaml) and do not conflate it with the parent docker-compose-server2.yaml.
